# ficium-portal-api — Design Document

_Last updated: 1 July 2026_

---

## 1. Why this service exists (ADR-001)

To keep the database's RLS-based security model while removing the hard dependency on Supabase's PostgREST. PostgREST is convenient but couples the platform to Supabase; replacing it with a thin FastAPI shell that sets `request.jwt.claims` itself makes the **entire data layer portable** to client cloud or on-prem with zero schema rewrite. This is the single most important design decision in the repo.

---

## 2. Thin shell, fat database

Business rules, tenancy, and maker-checker live in SQL (policies + SECURITY DEFINER functions). The API verifies the token, sets the claims GUC, and calls the SQL. Keeping logic in one place (the DB) avoids the classic drift between an API's idea of authorisation and the database's.

---

## 3. Endpoint design mirrors the old Supabase calls

Each portal route maps 1:1 to a call the frontend previously made against Supabase/PostgREST. This made the migration a swap, not a rewrite — the frontend changed a base URL, not its semantics.

---

## 4. Two auth paths, one claims shape

The portal and bank LOS systems have fundamentally different auth needs — browsers carry short-lived JWTs, backend systems need long-lived API keys. Rather than build two separate auth systems with incompatible plumbing, both paths resolve to the same claims dict:

```python
# JWT path (portal user)
{"sub": "...", "institution_id": "...", "auth_method": "jwt", ...}

# API key path (institution LOS)
{"institution_id": "...", "scopes": ["bids:write", ...], "key_id": "...", "auth_method": "api_key"}
```

`api_or_jwt_claims()` detects the path by prefix (`fic_live_` → key). `require_scope()` is a dependency factory that gate-checks scope for API key callers and transparently passes JWT callers through (they have full portal access). Every `/v1/` endpoint is typed once and works for both.

---

## 5. API keys: never store the raw key

API key format: `fic_live_<64 hex chars>` (32 bytes of CSPRNG output). Only SHA-256(raw_key) is stored in `institution.api_key.key_hash`. On lookup, incoming key is hashed and compared — if leaked from the DB, the hash cannot be reversed. Keys require maker-checker approval before activation. The raw key is shown exactly once at creation.

---

## 6. Webhooks: push over poll

Bank LOS systems should never need to poll for state changes. The webhook dispatcher (`app/core/webhooks.py`) fires signed HTTP POST events asynchronously (`asyncio.create_task`) on every business event. HMAC-SHA256 signing with a per-webhook secret lets the receiving system verify authenticity without a Ficium-to-bank shared key. Delivery receipts are stored in `institution.webhook_delivery` and surfaced in the portal for debugging.

---

## 7. /v1/ versioned public API

All machine-to-machine routes live under `/v1/`. This prefix is a stability contract — breaking changes (field removals, semantic changes) will go under `/v2/`. Additive changes (new optional fields, new endpoints) are made in-place. `/v1/` is generated by FastAPI and always has a machine-readable OpenAPI spec at `/openapi.json`.

---

## 8. Server-enforced compliance gate

`POST /v1/bids` (and the portal bid submission path) both check that the institution has an active `product_config` for the request's product type before accepting the bid. This is a server-side check — a bank cannot bid on products they are not configured for, regardless of what they send. The UI reflects this too, but the API is the enforcement point.

---

## 9. Service session vs tenant session for API key routes

JWT callers go through `tenant_session()` which sets RLS via the `auth.uid()` GUC. API key callers cannot use RLS because they don't carry JWT claims. Instead they use `service_session()` (privileged, BYPASSRLS) with explicit `WHERE institution_id = :iid` on every query. The result is equivalent isolation through different mechanisms. This is a known tradeoff — the alternative (synthesising a fake JWT for API key callers) was rejected as it would make RLS auditing harder to reason about.

---

## 10. Connection model

psycopg2 over the Supabase transaction pooler (6543); `SET LOCAL ROLE authenticated` inside `tenant_session()` so RLS actually evaluates (postgres role carries BYPASSRLS). No asyncpg — it requires a direct persistent connection, which pgbouncer transaction mode doesn't support.

---

## 11. Identity migration (ADR-002)

Tracks collapsing the ficium-auth vs Supabase `auth.users` identity spaces to one source of truth. Until done, `sub` parity keeps RLS resolving correctly.
